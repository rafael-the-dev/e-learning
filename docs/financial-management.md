# Financial Management Module

## Overview

The Financial Core Module handles billing and payment collection for student enrollments. It covers the full lifecycle from invoice creation through payment confirmation and receipt issuance.

## Domain Model

```
Enrollment
  └── Invoice
        ├── InvoiceItem[]
        ├── PaymentPlan?
        │     └── Installment[]
        ├── Payment[]
        │     └── PaymentSplit[]
        └── Receipt[]
```

## Models

### Invoice

Represents a billing document issued to a student for an enrollment.

| Field | Type | Description |
|-------|------|-------------|
| invoiceNumber | String | Unique per organization (e.g., `FAT-000001`) |
| status | String | `PENDING` → `PARTIALLY_PAID` → `PAID` / `OVERDUE` / `CANCELLED` |
| subtotal | Decimal | Sum of all item totals |
| discountAmount | Decimal | Applied discount |
| taxAmount | Decimal | Applied tax |
| totalAmount | Decimal | `subtotal - discountAmount + taxAmount` |
| paidAmount | Decimal | Running total of confirmed payments |
| balanceAmount | Decimal | `totalAmount - paidAmount` |

### InvoiceItem

Line items within an invoice. Cascade-deleted when invoice is deleted.

### PaymentPlan

Optional installment schedule linked to an invoice. One plan per invoice maximum.

| Field | Type | Description |
|-------|------|-------------|
| numberOfInstallments | Int | 2–60 |
| status | String | `ACTIVE` / `COMPLETED` / `CANCELLED` |

### Installment

Auto-generated by `CreatePaymentPlanCommand`. Amount distributed evenly; last installment absorbs rounding differences.

### Payment

Records a payment transaction against an invoice. Each payment has one or more `PaymentSplit` entries — the actual source of truth for how the payment was made.

| Field | Type | Description |
|-------|------|-------------|
| paymentNumber | String | Unique per organization (e.g., `PAG-000001`) |
| status | String | `PENDING` → `CONFIRMED` / `CANCELLED` / `REFUNDED` |
| method | String | Summary field — method of the largest split. Not the source of truth. |
| totalAmount | Decimal | Sum of all `PaymentSplit.amount` values |

### PaymentSplit

Breakdown of how a payment was made across multiple methods.

| Field | Type | Description |
|-------|------|-------------|
| method | String | `CASH`, `BANK_TRANSFER`, `MPESA`, `EMOLA`, `POS`, `CARD`, `CHEQUE`, `OTHER` |
| amount | Decimal | Amount paid via this method. Must be > 0. |
| reference | String? | Optional reference number (e.g., M-Pesa transaction ID) |
| notes | String? | Optional notes for this split |

**Rules:**
- A payment must have at least one `PaymentSplit`.
- Each split `amount` must be > 0.
- The sum of all `PaymentSplit.amount` values must equal `Payment.totalAmount`.
- `Payment.method` is populated automatically with the method of the highest-value split.

### Receipt

Issued only after a payment is confirmed. One receipt per payment.

| Field | Type | Description |
|-------|------|-------------|
| receiptNumber | String | Unique per organization (e.g., `REC-000001`) |
| status | String | `ISSUED` / `CANCELLED` |

## Business Rules

1. `invoiceNumber`, `paymentNumber`, `receiptNumber` are unique per organization.
2. `totalAmount = subtotal - discountAmount + taxAmount`
3. `paidAmount` cannot exceed `totalAmount`.
4. `balanceAmount = totalAmount - paidAmount`
5. A payment must have at least one `PaymentSplit`; each split amount must be > 0.
6. `Payment.totalAmount` is computed from the sum of `PaymentSplit.amount` values.
7. `Payment.totalAmount` (sum of splits) cannot exceed the invoice's current `balanceAmount`.
8. A receipt can only be issued after payment is in `CONFIRMED` status.
9. An invoice with `paidAmount > 0` cannot be cancelled.
10. Financial records are never hard-deleted (`deletedAt` soft-delete on Invoice).
11. Payment creation (including splits and invoice balance update) is fully transactional.

## Numbering

Sequential numbers per organization are generated at command execution time using `getLastXxxNumber()` + 1. Format: `PREFIX-NNNNNN` (zero-padded to 6 digits).

- Invoices: `FAT-000001`
- Payments: `PAG-000001`
- Receipts: `REC-000001`

## Multi-Tenancy

- `organizationId` is always resolved server-side via `requireOrganization()`.
- Never accepted from client input.
- All repository queries include `organizationId` in every `where` clause.
- Cross-tenant validation: when an action references a foreign key (e.g., `studentId`, `enrollmentId`, `invoiceId`), the command verifies it belongs to the same organization before proceeding.
